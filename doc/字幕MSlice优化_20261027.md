# 字幕扩展后的 MSlice 超限优化

## 编译证据

本机最新综合报告 `src/td_project/lab_ex5_i2s_v1.0_Runs/syn_1/lab_ex5_i2s_v1.0_gate.area`：LUT 17,955/19,600，寄存器 9,874/19,600，BRAM9K 64/64，DSP 18/29。字体分块已生效，占14块BRAM；整个字幕模块占16块BRAM。

`phy_1/run.log` 报 `PHY-9009 ERROR: Design's mslice number = 5219, exceeds the limit 4900`，超出319个，约6.5%。本次失败是逻辑打包/物理资源不足，已不是前次65块BRAM超限。LUT未达到100%并不保证MSlice能放下，最终打包受连线、控制与布线优化影响。

RTL面积报告中 `subtitle_unicode_map` 的组合逻辑计数为17,270，不能当作最终LUT数；它提示大规模并行字符比较。Gate报告中整个字幕模块为2952 LUT加261 ripple项，font子模块仅12 LUT，map边界报告仅16 LUT但大量逻辑已被展平/移出层级，因此不能根据map那一行认为字符转换只消耗16 LUT。现有证据支持先优化UART字符映射，但尚不能给出修改后的实测节省量。

## 本次修改

生产UART接收器不再调用16位Unicode全表并行比较，而是使用 `subtitle_unicode_lookup`：将334个非ASCII字符按码点排序，通过9位索引选择25位表项（16位码点、9位字形编号），用一组比较器在若干时钟内二分查询。ASCII仍直接写入；不支持的字符仍显示问号。原组合map仅保留作独立仿真参考，不接入生产顶层。

50MHz、115200/8N1时两个字节间隔约4340拍，查找十余拍即完成，不影响字幕输入速度；地址在请求时锁存，完成后写回同一双缓冲RAM。RAM保留单写口。分句字幕使用已编译的字形编号，不经过UART查询；音频样本计数、视频两拍流水线、开场动画和原字库内容均不改。生成器同步修改，重新生成不会恢复旧的生产映射路径。

本次没有新增显式BRAM数组、DSP、帧缓存或TF卡读取流程；期望主要降低LUT/MSlice压力。实际表项实现、LUT、BRAM及MSlice占用仍以新综合/物理报告为准。本次未运行TD综合、布局布线或位流生成，不承诺仅此一项必然解决5219超限。

## 关于从TF卡加载字库

这个方向对后续每张图片都有字幕更合适，但必须同时移动字形点阵、字符编号和句表，只把TXT文字搬出去而保留全部字体与Unicode并行映射，不能解决当前根因。可在电脑端将每张图片的SRT与字形预编译成二进制包，板上只保留当前图片的一份字形/句表缓存，按实际PCM样本推进，不在FPGA解析UTF-8/SRT。

需要在切图后、PCM起播前完成加载，并与现有BMP、PCM读卡仲裁配合；必须保证加载完整后再发布、取消过期请求、预读不覆盖正在显示的字形、首句不丢失和音频不因读卡争用欠载。因此动态版是一次完整读取链路改造。本次先按用户允许的自主优化路径处理查找逻辑，保留静态版的稳定同步行为，未将卡上动态加载表述为已实现。

## 验证

新增 `tb_subtitle_unicode_lookup.v`，对除ASCII直通区外的BMP范围逐个码点与原组合映射对照，检查命中、缺字、完成时间及复位取消。主机测试核对查找表顺序和字形编号。

已通过四项主机测试、640×480真实UART输入/UTF-8/换页、字体分块、开场、图4～6八句时间轴和循环同步、音频波形，以及顶层编译、十图缓存、缩略图和拨码回归；`git diff --check` 通过。这些验证确认功能行为，不代表TD资源或时序验证通过。

下一次在TD先重新综合，再运行物理流程；报告必须来自当前修改，不能复用旧数据库。如果仍超限，保留本次改动，以新报告决定是否继续处理显示坐标/宽运算，或进入动态字库方案。
