# 第五张加载 E45 排查（2026-10-28）

用户已反馈：重新构建并下载诊断版后，图片加载恢复正常，当前工程可以正常使用。按用户要求保留该版本及诊断字段，不再修改功能。E45 的根因尚未确认，不能据此认定诊断字段本身修复了短帧问题。

COM3、115200、8N1 捕获到复现：前四张加载完成，`T=4 E=00 J=04`；第五张先进入 `T=3 J=05`，约两秒后变为 `T=2`，再等待约五秒后为 `T=F E=E0 J=05`。卡目录识别十张，`M=03FF U=0A`。原始日志保存在本地 `tests/build/uart_e45_20261028.log`。

屏幕 E45 来自 `media_frame_loader`，表示已收到帧结束，但接收或生成写命令的像素数不是完整一帧。UART 原来的 E 字段没有包含 writer 错误，所以它显示调度器稍后的 E0 超时；两项并不矛盾。仅这些信息不能区分漏像素、提前结束、文件内容或硬件时序原因。

精简 UART 日志现增加：

| 字段 | 含义 |
| --- | --- |
| WR | 帧写入器错误；45 为像素不足 |
| RX | 本次加载收到的像素数量，五位十六进制 |
| WX | 本次加载已生成写命令的像素数量，五位十六进制；不代表 SDRAM 已排空 |

正常 640×480 的 RX、WX 都是 `4B000`。计数在写入错误后停止，下一次加载或复位清零。错误和两项计数通过同一个握手邮箱跨到 UART 时钟域，每一行冻结同一快照。保留原 E 字段，不覆盖调度器错误。

最近已有布局布线报告（19:26:37）显示 SD 域运行于 100 MHz，最差建立裕量 -4.725 ns，报告 Fmax 约 67.912 MHz；SDRAM 控制域也有 -0.255 ns 建立违例。这是实际稳定性风险，但还不能凭报告断定 E45 的唯一原因。本次未修改时钟、图片数据流或错误保护，也没有运行 TD 或生成新 bit。

验证通过：精简 71 字节与完整 230 字节 UART 实际收发、行内快照保持；四 bank 写入／读取、CDC 背压、解码和短帧错误；按当前 TD 源列表的顶层 RTL 展开（厂商 IP 按黑盒处理）。

若以后再次出现 E45，可连接串口、关闭 SW1、按 KEY1 复位，再切到第四张触发第五张预缓存，采集 WR/RX/WX 字段。目前无需继续复现或修改。
