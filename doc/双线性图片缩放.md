# 双线性图片缩放（2026-10-15）

本次参考“第十三讲：图片缩放与缩略图”目录中的第 12 课讲义及 `bilinear_8q8.v`、`thumbnail_layout.v`，实现了加载时的双线性缩放。参考插值模块未完成全部 RGB 通道，本工程实现三个通道的完整定点运算，并补上文件缓冲、行缓存与帧完成握手。缩略图布局尚未接入。

## 现在能看到什么

卡根目录继续使用 `PIC1.BMP`～`PIC16.BMP`。图片读入时自动适配 640×480，无需开启缩放开关；成功写入缓存后按原有方式显示和转场。另已增加按键交互缩放，见下文。

| 原图 | 显示结果 |
| --- | --- |
| 320×240 | 横纵各放大约两倍，边缘产生渐变中间色 |
| 800×600 | 缩小到 640×480 |
| 1920×1080 | 缩小并拉伸到 640×480，宽高比例会改变 |
| 640×480 | 原像素直通，不重新插值 |
| 竖图或其他比例 | 铺满屏幕，会变形 |

支持宽 1～1920、高 1～1080 的正高度、24 位、无压缩 BI_RGB BMP，支持 BMP 每行的四字节对齐填充。单行、单列图片会沿相应方向复制。负高度、32 位、压缩 BMP 和超过上限的图片仍会报错。

双线性放大比最近邻复制像素平滑，但不会恢复原图缺少的细节；文字和线条可能变柔和。大倍率缩小只取四个相邻像素，没有面积平均或专门的抗混叠滤波，密集纹理仍可能有摩尔纹。

旧图片已缓存时，切换仍使用原有转场；新图未就绪时沿用原有加载等待流程。当前没有拖动、多图缩略图菜单，也没有按源图宽高比自动留边。

## 按键交互缩放（2026-10-15）

当前图片完整显示后，长按实体 KEY3 约一秒进入缩放模式；持续按住不会反复切换模式，也不会切换音源。再长按退出。KEY3 的短按仍切换 PCM／图片琶音，但改在消抖后的松开时执行。

| 缩放模式操作 | 效果 |
| --- | --- |
| KEY2 按下再松开 | 增加一档倍率 |
| KEY4 按下再松开 | 降低一档倍率 |
| 0.5× | 图像为 320×240，居中显示，四周补黑 |
| 1× | 标准 640×480 帧完整显示 |
| 1.5× | 居中放大，超出屏幕的部分裁掉 |
| 2× | 将中间 320×240 区域放大到全屏 |

倍率到达上下限后保持，不循环。参数只在读帧边界锁存，按键不会让同一帧上半部、下半部采用不同倍率。模式内暂停轮播，不改变轮播开关；退出后按原设置从零重新计时，当前倍率保留，换图恢复 1×。黄色 `ZOOM 1.5X` 等文字表示模式已开启，退出后非 1× 倍率仍显示白字。模式内 KEY2／KEY4 不执行切图、上一张或轮播开关动作；缓存预读和音频继续工作。

这里分成两个处理阶段：读卡时仍对源 BMP 做双线性插值，写入标准帧；按键缩放则对这张标准帧作最近邻采样。交互放大可能看见像素块，不会恢复源图在第一次适配时丢掉的细节。这次没有再增加实时双线性乘法流水线，以控制已有资源和时序压力。

读侧增加一块同步行 RAM：先按连续突发读取完整的 640 像素源行，再按倍率采样成一行输出，送入原有异步 FIFO。放大重复读取相应源行，缩小跳过相应行；黑边行也读取一行，使每帧仍恰好读取 307200 个 SDRAM 字。没有在一个 SDRAM 突发内插入重复地址或跳跃地址，不依赖加密控制器支持随机像素访问。转场仍按输出行选择新旧 bank，不增加整帧缓存。

行 RAM 声明为 `1024×24 bit`，使用工程已有的安路 BRAM 推断属性；存储容量约 3 KiB，实际 BRAM 打包数量、LUT 和时序须以重新综合结果为准。1× 保留原读流路径。交互坐标由加法和相位计数推进，不需要变量除法或颜色乘法。

`tests/tb_image_zoom.v` 使用真实 reader、行 RAM、异步 FIFO 和预取模块，逐个检查四档倍率的源地址与 RGB，覆盖连续切换倍率、帧内改参数不生效、新旧 bank 混合以及读行中复位。完整尺寸用例以 25MHz 连续有效像素、每行 160 拍消隐读取 640×480，检查无 FIFO 欠载；内存模型提供八拍有序返回，不等同于实板 SDRAM 仲裁与物理时序验证。按键用例检查长短按隔离、倍率饱和、轮播暂停／恢复和切图恢复 1×。

运行 `./tests/run_transition_tests.ps1 -FullSize` 可执行这些用例及原有转场、缓存、音频提交回归。此次没有启动 TD 或生成位流，下一步由用户重新构建并上板确认按键、画面和资源报告。

## 为什么放在加载端

```text
TF / FAT 字节流
  → 1024 字节 FIFO（整扇区接收，解码可暂停）
  → BMP decoder（原图尺寸，BGR 转 RGB）
  → 双行 RAM + 双线性 scaler（固定输出 640×480）
  → media_frame_loader（统一做一次上下翻转）
  → 写侧 CDC → 四块 SDRAM 帧缓存
  → 原有 reader / 擦除转场 / OSD / HDMI
```

已有 reader 按标准整帧顺序取数，不适合直接为每个显示像素随机读取四个原图像素。加载时完成插值后，四缓存仍然每块保存 307200 个 32 位像素字，不增加显示端 SDRAM 读取量，也不用改变视频与同步信号的延迟关系。

两行缓存按原图物理行号的奇偶交替保存。收齐插值所需的相邻行后暂停输入，生成能够生成的目标行，再继续读原图。缩小时跳过不需要的行，放大时复用同一对行。两行有效数据最多占 `2×1920×24=92160 bit`；存储深度按二次幂补齐为 2048，实际声明 `2×2048×24=98304 bit`，即 12 KiB，另有 1 KiB 字节 FIFO。具体 BRAM/DSP 映射与时序必须看本地综合报告。

SD 读一个扇区后不能逐字节暂停，因此只暂停 FIFO 的解码出口：分配 BMP 扇区前，至少留出 512 字节加流水余量。PCM 继续在整扇区边界优先补充，不能把 SD 的忙信号当作像素 ready。

缩放器输出是脉冲像素流，下游仍由原有 loader/FIFO 接收，不提供逐像素 ready 握手。缩放运算分拍执行，640×480 同尺寸路径保留原有输入速率。

## 插值怎么算

以左上角为原点说明公式；硬件处理 BMP 自底向上的物理行，loader 最后统一翻转。输出坐标 `(u,v)` 对应原图坐标：

```text
x = u × (原图宽−1) / (输出宽−1)
y = v × (原图高−1) / (输出高−1)
```

取 `(floor(x),floor(y))` 附近四点，先横向插值两次，再纵向插值一次，每个 RGB 通道分别计算：

```text
top    = p00 × (1−fx) + p10 × fx
bottom = p01 × (1−fx) + p11 × fx
result = top × (1−fy) + bottom × fy
```

坐标采用端点对齐，步长为 Q16 定点数；每张图开始时用共享的逐拍除法器分别计算横纵步长，随后累加推进。权重取小数的高八位，范围 0～255，分母 256。最后一列/行强制落在原图末端，邻点钳位到边界。

横向结果保留八位小数，纵向完成后才舍入为八位颜色，避免每一级都取整。三个通道各复用一条有符号乘法路径，依次计算上行、下行、纵向插值；不是复制十二个独立的颜色乘法器。

在 100 MHz、输入数据已到达且不受其他停顿影响时，插值路径每个目标像素约八拍，整张图的插值部分约 25 ms。这个数字不是实际读卡总耗时：大图还必须读完整源文件，1920×1080 RGB24 像素约 6.22 MB；PCM 补充和卡速也会影响等待时间。原有约五秒的加载超时未调整，慢卡加载大图可能超时，建议先用 320×240 和 800×600 上板验证。

## 完成与失败处理

不能把 FAT 文件读完直接当成新帧可显示。现在必须同时满足 BMP 解码校验成功、缩放器输出完所有目标像素，才产生 `frame_commit`；之后仍要等待原有 loader/CDC 写入排空。截断、尺寸错误、FAT 错误和中止均不能发布半帧。文件尾部 padding 或其他尾随字节继续排空，不因最后一个目标像素已生成而卡住。

## MSlice 超限的定位与修正

用户本地构建曾报 `Design's mslice number = 7524, exceeds the limit 4900`。读取该次已有 `syn_1/lab_ex5_i2s_v1.0_gate.area`，整机 LUT 为 26827/19600（136.87%）；其中 `u_scaler` 为 14252 LUT、0 BRAM、3 DSP。日志记录了分布式 RAM 的推断和打包，说明主要问题是两行缓存未映射到块 RAM，并非双线性运算的三个 DSP 耗尽。

修正版在两个行数组上使用与工程安路官方 FIFO 相同的 `/* fehdl force_ram=1, ram_style="bram" */` 指示，将深度规整为 2048，读写地址收窄到 11 位，并拆成独立的无复位同步读写进程。同尺寸直通时不再写行缓存。输入尺寸上限和插值算法保持不变。

这次资源修正没有运行 TD。重新综合后应检查 `u_scaler` 的 BRAM 非零、LUT 显著下降以及最终 MSlice 是否低于 4900；实际资源数字与时序收敛不能用行为仿真代替。

## 第二张加载超时修复与串口快照（2026-10-15）

板上报告 `T=F E=E0 V=1 F=F J=02 K=00000027 Z=000E1036`。
其中 `F=F` 是 PIC1～PIC4 的目录有效位，不是错误码；`J=02` 表示正在加载播放列表第二张，`E0` 是调度器五秒加载超时。`Z` 为 921654 字节，符合标准 640×480 RGB24 BMP 的大小，但仅凭文件长度不能确认图片头尺寸。

新增连续文件仿真后复现：第一张结束留下 `decoder_finished=scaler_finished=1`。第二张收到写端 ACK 时，状态进入 STREAM，同时寄存 `decoder_start=1`；FIFO 完成标志要到下一拍才响应这个启动信号清零。原代码在这一拍使用上一张的完成标志，错误地产生提交并退出 STREAM。之后第二张文件虽然开始读取，但 FIFO 不再出队，最终等不到完整 SDRAM 写入而超时。

修复是在 `frame_commit` 和 STREAM 完成判定上增加 `!decoder_start`，等新事务的清零拍结束再判断完成。测试增加不复位的直通→直通、直通→缩放、缩放→缩放、缩放→直通逐像素/写地址检查。此用例在修复前出现 `Premature scaled frame commit`，修复后通过。

UART 每行末尾增加 `H=0123456789ABCDEF`（64 位十六进制）。正常时显示当前进度；调度器决定超时的同一拍冻结，保留到复位或下一次加载，不会被下一拍 abort 清零覆盖。无需手工解码，反馈完整日志即可。

| H 位段 | 含义 |
| --- | --- |
| 63:62 | 图片源状态：0 空闲、1 等待写端 ACK、2 STREAM、3 音频 |
| 61:58 | scaler：0 等头、1/2 求步长、3 收集源行、4 检查行、5～12 插值、13 完成、14 同尺寸直通 |
| 57:56 | 扇区归属：0 无、1 BMP、2 PCM |
| 55,54 | BMP 头通过、scaler 可接收 |
| 53,52 | BMP 解码完成锁存、缩放完成锁存 |
| 51,50 | FAT 文件结束待排空、结束已送 decoder |
| 49,48 | FAT 图片流忙、帧写端 ACK |
| 47,46 | 调度器已见图片源完成、已见 SDRAM 写完成 |
| 45:44,43 | 调度器查表准备阶段、加载忙 |
| 42:32 | 图片字节 FIFO 占用（0～1024） |
| 31:0 | 当前文件已出 FIFO 的字节数，每张从零开始 |

UART 仿真检查完整 126 字节及发送期间快照稳定；缓存调度仿真检查“源完成、写入未完成”的超时快照，确认 abort 后仍保留原状态。
